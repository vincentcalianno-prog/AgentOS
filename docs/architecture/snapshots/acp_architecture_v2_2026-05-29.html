What changed since v1

Delta from snapshot v1 (2026-05-28)

v1 captured the layer architecture and a two-taxonomy sketch (ContractType, Category) before any playbook schema design existed. Step 2b expanded the schema model from two top-level taxonomies to a 13-entity system covering taxonomies, positions, overlays, runtime concessions, and resolution provenance. The layer architecture itself is unchanged — agents stay where they were — but Layer A now contains substantially more substrate, and the relationships between entities are formally modeled.

  • Schema model (new in v2) — 13 entities locked: ContractType, ContractRelationship, Category, SubClause, PlaybookEntry, Pattern, Overlay, CrossClauseDependency, ResolutionResult, RuntimeConcession, AuthorizationEvent, RequiredAuthorization, ConcessionPromotion.
  • Contract type taxonomy expanded — 7 types (added MOU/LOI based on Vincent's negotiation history). 9 initial relationships (PO and SOW operate under MPA, MEPA, and MSA; NDA references all three master types). MOU/LOI is standalone.
  • Three-axis overlay system — counterparty, project, commodity. Hardcoded for now with cheap-extension design. Most-restrictive-wins resolution. Loosening handled separately via RuntimeConcession.
  • Concession-vs-overlay distinction — overlays are static, pre-declared, risk-driven tightening. Concessions are dynamic, runtime, human-authorized loosening. Two distinct mechanisms with separate audit trails.
  • Provenance as resolution result — computed at query time, stored in audit log per ClauseRecommendation. Every effective position is traceable to (baseline + contract_type_override + overlays + resolution_rule).
  • DNA/cells extraction rule documented — workflow #2 candidate extractions flagged (Agents 1, 2, 7) but not committed. Extract only on byte-for-byte duplication, not theoretical similarity.
  • Commit state advanced — branch is now at 3f29225 (4 commits ahead of yesterday). Schema design archived at docs/architecture/playbook_schemas.md.

Layer A / B / C architecture (refined)

The layer structure is unchanged from v1 — Layer A is the umbrella, Layer B is the workflow substrate split into Platform DNA and Workflow Cells, Layer C is Antora-specific deployment content. What's evolved is the substance of each layer.

Layer A — AgentOS. Now holds 13 schema entities defining how contract types relate, how clauses are organized, how positions are expressed, how overlays modify positions, how runtime concessions are authorized, and how resolution provenance is tracked. See Diagram 2 for the entity model.

Layer B — WorkflowOS. Added "Loaders & resolvers" to the Platform DNA region. These are the workflow-agnostic mechanisms that read Layer C content, validate it against Layer A schemas, and resolve effective positions at query time. The agents themselves are unchanged from v1.

Layer C — Deployment. Now shows four buckets: playbook content (the instances Antora authors), skills (LLM reasoning patterns), deployment config (credentials, routing, SLA), and runtime state (negotiations in flight, audit log, concession log). The playbook content bucket is where Step 2c authoring will happen.

Diagram 2 of 3

13-entity schema model

The schema model organizes into three clusters, each playing a different role in the system.

Taxonomy entities (teal)

Define what kinds of things exist — the vocabulary of the domain. ContractType enumerates the contract types (NDA, MPA, MEPA, MSA, SOW, PO, MOU/LOI). ContractRelationship captures parent/child relationships between types (PO and SOW operate under master agreements; NDA references master agreements). Category and SubClause define the hierarchical organization of clauses within contracts. These four entities are pure substrate — every deployer uses the same taxonomy entity types, populated with their own instances.

Position entities (coral)

Define the actual judgment about what's defensible, acceptable, and unacceptable. PlaybookEntry is the per-(ContractType, Category, SubClause) entry holding defend_baseline, accept_modifications, and reject_thresholds. Pattern is the reusable unit inside accept and reject lists. Overlay applies context-specific tightening based on counterparty, project, or commodity. CrossClauseDependency captures inter-clause risks like the MCM finding (consequential damages + direct damages clarification interaction). These five entities hold the substance of the playbook.

Runtime entities (amber)

Capture what happens during negotiation. ResolutionResult is the computed effective position for a specific query, including the provenance trace. RuntimeConcession captures human-authorized loosening — Antora accepting a supplier counter that's less favorable than the resolved position. AuthorizationEvent records who approved the concession with what role and when, governed by RequiredAuthorization policy. ConcessionPromotion captures the deliberate human act of promoting repeated concessions into a permanent Overlay. These four entities make the agent's reasoning auditable.

All 13 entities are Layer A substrate — their schemas are universal and port across deployments. The instances of each entity are Layer C content — Antora's specific contract types, categories, playbook entries, overlays, and runtime data. Schema in Layer A; content in Layer C.

Diagram 3 of 3

Overlay resolution flow

The resolver lives in Layer B (as part of the loaders subsystem). When any agent — typically Agent 5 (Clause Analyzer) or Agent 6 (Counter Proposer) — needs Antora's effective position on a specific clause in a specific negotiation context, it queries the resolver.

The resolver looks up the baseline PlaybookEntry for the (ContractType, Category, SubClause) triple, finds applicable overlays based on the negotiation context (which counterparty, which project, which commodity), and applies them using most-restrictive-wins semantics. For list fields (accept modifications, reject thresholds), this means unioning all add_to operations and applying remove_from operations. For numeric constraints (cap multipliers, warranty months), most-restrictive means selecting the maximum value across all applicable overlays.

The result is wrapped in a ResolutionResult that includes both the effective entry and a provenance trace listing each source that contributed. When Agent 5 produces a ClauseRecommendation based on the resolved position, the audit log stores the full provenance — which makes every recommendation traceable back to baseline + overlays + resolution rule.

Loosening is intentionally not handled by overlays. If a supplier counter is less restrictive than the resolved position but Antora's team wants to accept it, that's a RuntimeConcession — a separate runtime mechanism with multi-party human authorization. Concessions are scoped to a single negotiation and never auto-promote into permanent overlays. Promotion to overlay is a deliberate, reviewed, human act captured as ConcessionPromotion.
